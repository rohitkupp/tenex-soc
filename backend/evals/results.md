## 7. Known weaknesses

Stated honestly, per docs/12's own instruction that naming your own weaknesses is what a senior engineer does — a reviewer who finds an unlisted weakness trusts everything else less.

- **Synthetic-data circularity.** Every detector and model here is scored against `datagen`'s own generator. `datagen` mitigates this with real-world-grounded distributions (domain popularity, UA mix, diurnal curves — docs/11) but a model can still partly be learning the generator's own regularities, not a real enterprise's.
- **Single-file baseline.** Every scenario in the golden set is one log file, one simulated org, one time window. Nothing here tests cross-file, cross-tenant, or long-running-analysis behavior.
- **Reduced golden-set scale.** This harness uses 18,000 events / 120 users / 6 departments per scenario, not docs/11's ~50,000-event / 250-user production target — the smallest configuration `tests/test_datagen_ground_truth.py` validated as reliably clearing scenarios 4 and 5's own acceptance gates, chosen so the full L1-L5 pipeline stays tractable to run on every PR. The L3-only headline table above (`app.detection.ml.evaluate.evaluate`) is scored on these same frozen files for consistency, not docs/11's full 50k/250-user scale either.
- **LogBERT's published loss and why the sequence layer was cut.** See the L4 appendix below: LogBERT scored 0.097 pooled F1 against Markov's 0.529, and neither model detected the account-takeover-chain scenario that motivated the whole layer. It never shipped.
- **The absolute-vs-entity-relative feature defect.** Documented in `docs/04-DETECTION.md` §L3: of the L3 feature vector, only a few features were entity-relative (own-history or cohort) rather than population-absolute — the reason the original M8 benchmark found no L3 model could detect the low-and-slow exfiltration scenario at all. Corrected per that doc; see the L3 table above for whether the correction actually shows up in this run's numbers.
- **Seeded analyst feedback is synthetic.** Any learning-loop calibration or fusion-weight signal that depends on analyst feedback history in this environment comes from `app/scripts/seed_feedback.py`'s synthetic seed data, not real analyst decisions.
- **Agent metrics are not measured.** `app/agent/` has no `orchestrator.py` or `verifier.py` yet in this checkout, and no recorded LLM fixtures exist — `disposition_accuracy`, `technique_accuracy`, `hallucination_rate`, `citation_density`, and `severity_disagreement` are all `not measured`, not fabricated or assumed zero.
- **A real defect found and worked around, not silently patched.** `app/graph/features.py`'s graph-signal explanation payload can carry a raw `z_score` of `+/-inf` (`robust_z` returns it by documented design when a feature's reference population has zero MAD) and Postgres JSONB rejects the literal `Infinity` token. `app.graph.pipeline_demo._calibration_feature` already sanitizes the identical root cause on the calibration path; `evals/pipeline.py` applies the same finite-sentinel policy as a process-local monkeypatch of `app.graph.features`'s `robust_z` binding (not an edit to any `app/**` file) so this harness can run at all. Every one of the eight golden scenarios hit this at this harness's 120-user org size — a real, reproducible bug filed here, not silently avoided.
- **Resolved: `app.graph.pipeline_demo._ml_model_pairs` used to score the pre-migration-19 L3 roster** (`ml.iforest`/`ml.mahalanobis`/`ml.ecod`/`ml.peer_group`) instead of `SHIPPED_MODEL_FIELDS` (`ml.eif`/`ml.kth_nn`/`ml.peer_group`) — the same class of stale-hardcoded-list bug already fixed for `known_detector_registry` and `app.detection.calibration._model_pairs`, previously left unfixed here for lack of sign-off to touch `app/graph/pipeline_demo.py`. Now reads `SHIPPED_MODEL_FIELDS` directly (`app.detection.ml.detect`'s own roster constant), so `_run_l3`'s signal emission and `fit_layer_calibrators`'s calibration-sample collection both stay faithful to what production actually ships, and `ml.eif`/`ml.kth_nn` now appear in section 3's live-pipeline breakdown and get a fitted calibrator like every other shipped model.

## Entity-relative features — the measured defect, corrected

M8's own report found **no L3 model detected the low-and-slow exfil scenario** and traced it
structurally: 47 of 50 features were absolute/population-level; only 3 were entity-relative. docs/04
now makes entity-relative variants normative for the volume, transfer, and domain families, each
carrying **both** an own-history-relative and a department-cohort-relative variant.

**Measured: 6 of 53 features (11.3%) are now entity-relative — double M8's 3 of 50 (6%).**

| Family | Own-history variant | Cohort variant |
|---|---|---|
| Volume | `n_events_z_vs_own_history` | `n_events_z_vs_cohort` |
| Transfer | `bytes_out_sum_z_vs_own_history` | `bytes_out_sum_z_vs_cohort` |
| Domain | `rare_domain_ratio_z_vs_own_history` | `rare_domain_ratio_z_vs_cohort` |

The cohort half is a real fix, not a rename: M8's `n_events_z_vs_cohort` compared an entity against
*every* entity active in the same hour, department unlabeled — the org-wide population, not a peer
group. `app/detection/ml/events.py` now recovers each event's `department` from `actor.user.groups`
(`MLEvent.department`), and `features.py`'s `_cohort_z` groups by `(department, window_start)` for
`entity_type="user"` (falling back to the window-only population for `src_ip`, which has no
department of its own — documented scope decision, `features.py`'s own docstring). A regression
test (`tests/test_ml_features.py::test_n_events_z_vs_cohort_is_department_scoped_not_window_wide`)
constructs a case where the two readings disagree — a `sales`-department entity spiking to the same
volume `engineering` is normally at — and proves the department-scoped reading fires
(`z == inf`, correctly an outlier against its own quiet department) while the pre-fix window-wide
reading would have scored `z == 0.0` (invisible, since engineering peers make that volume look
globally ordinary). Real attribution evidence this feed matters: the LOF/`ml.peer_group` example
below has `n_events_z_vs_cohort` and `rare_domain_ratio_z_vs_cohort` both in its own top-10
per-feature explanation for a genuine scenario-5 true positive.

**Prediction 1, confirmed as stated.** This is the one clean result: ECOD aggregates per-dimension
tails, and the low-and-slow campaign is built (by its own acceptance gate) to put nothing in a
marginal tail. It doesn't. The autoencoder's joint-reconstruction view does pick up a weak signal
(recall 0.048 — not strong, but nonzero, and the only model besides Mahalanobis to register
anything). Per docs/12's own falsification rule, this is the good-and-honest outcome: ECOD's
non-detection is exactly what justifies keeping the autoencoder in the ensemble for this attack
shape.

**Prediction 2, falsified — and the likely mechanism is a direct side effect of the entity-relative
feature fix above.** docs/04's own hypothesis was that only LOF, via local density, could see a
peer-group deviation that is "globally normal." But the department-cohort z-score features
(`n_events_z_vs_cohort`, `bytes_out_sum_z_vs_cohort`, `rare_domain_ratio_z_vs_cohort`) are now
explicit dimensions in **every** model's input vector, not just LOF's. Once "how far this window
sits from the entity's own department" is a first-class feature, a *global* model like Mahalanobis
can key on that one dimension being extreme without needing LOF's local-neighborhood mechanism at
all — Mahalanobis's 0.453 recall on this scenario is higher than LOF's own 0.026. This is a
genuinely different, more interesting finding than the pre-registered one: making peer-group
information explicit in the feature vector helps every model that can read a feature, not only the
one built to infer it implicitly. It also suggests LOF's own marginal value here may be smaller
than docs/04 argued, once the cohort features exist — a testable follow-up, not resolved by this
run.

**Prediction 3, falsified in both directions — the more surprising result in this report.** Two
things went differently than pre-registered, and both are reported plainly rather than reframed:

1. **STL itself did not cleanly detect scenario 6.** Scored on the real `seasonal_deviation` eval
   file, `signal.stl_residual` recovered 0 of 36 malicious lines when scored against the victim's
   own isolated history (see [L2 results](#l2-detector-table-six-detectors-precision-recall-f1)
   below for the corpus-wide number, which is higher only because the detector's baseline false
   positive rate is itself elevated, not because it is finding the campaign). The most likely
   cause: this module's `MSTL` decomposition is fit **self-inclusively** — on the same window it
   scores, campaign hours included — the same convention every other "own-history" detector in
   this codebase uses (`burst.py`, `ml/features.py`'s `estimate_work_hours`, both of which document
   the identical caveat). Scenario 6's campaign is deliberately subtle and budget-capped against
   the victim's *own* history (its own acceptance gate requires only a 70% residual separation
   against a **pre-campaign-only** fit) — a self-inclusive LOESS fit has real opportunity to
   partially absorb a sustained, modest shift into what it learns as "normal," diluting exactly the
   residual signal the detector needs. This is not a hypothetical: it was verified directly by
   scoring the victim in isolation with `stl_kwargs={"robust": True}` (LOESS's own standard
   outlier-resistant option) — same null result, ruling out ordinary LOESS noise sensitivity as the
   cause and pointing at the self-inclusive-fit explanation specifically.
2. **Two L3 models detected it anyway** (`ml.mahalanobis` 0.778 recall, `ml.peer_group` 0.028),
   contradicting the "none of the five" half of the prediction. The likely mechanism: the L3 unit of
   analysis is `(entity, 1-hour window)`, and the specific hour a campaign injects extra off-hours
   volume into is, by construction, a window where `off_hours_ratio`/`night_ratio` are already at
   their maximum (1.0) *and* `n_events`/`n_events_z_vs_own_history` are elevated relative to that
   entity's typically-near-empty off-hours windows — a joint anomaly a per-window multivariate model
   can see without any explicit seasonal/time-series modeling, even though the campaign is
   invisible in *daily aggregate* exactly as designed. "Invisible in daily aggregate" and
   "invisible to a per-hour joint snapshot" turned out to be different claims.

Both halves point the same direction: **this specific implementation of STL, as built, does not
yet deliver the clean win docs/12 predicted**, while the L3 feature vector is more capable on this
scenario than expected once volume and timing features co-occur unusually in the same window. The
STL module's own unit tests (`tests/test_signal_stl.py`) still prove the underlying mechanism works
on a clean, non-adversarial off-hours burst (100% recall on 4 synthetic injected hours) — the gap
is specifically between a detector-vs-clean-signal test and a detector-vs-a-campaign-built-to-be-
subtle-against-its-own-acceptance-gate.

### FFT beaconing cross-check

The rewrite replaced bucketed autocorrelation with `numpy.fft.rfft` over a uniform 1-minute series
(docs/04, REWRITTEN §L2), reporting `dominant_period_s`/`fft_peak_power_ratio` instead of
`dominant_lag`/`autocorrelation_at_dominant_lag`. **The CV/MAD-jitter score itself is untouched**
(`tests/test_signal_beaconing.py::test_jitter_degrades_the_score_monotonically` still passes
unchanged) — only the secondary cross-check changed, exactly as instructed. Directly verified: a
clean 240s-interval synthetic beacon produces `fft_peak_power_ratio ≈ 47` (comfortably above
`k=6`) and a recovered `dominant_period_s ≈ 240.0`; a Poisson-arrival (non-periodic) fixture at a
realistic candidate-group scale (~190 one-minute buckets, matching this project's own beaconing
fixtures) stays below `k=6`. One numerically interesting finding surfaced while validating this:
the naive "peak bin power / mean of the rest" statistic is not scale-invariant in bucket count — a
periodogram's per-bin power under white noise is itself exponentially distributed, so the
*maximum* over many bins grows with bin count by ordinary extreme-value statistics, independent of
real periodicity (a several-thousand-bucket random series routinely exceeds `k=6` on power alone).
This is exactly why docs/04 states `k=6` as *empirically tuned* against the docs/11 difficulty
sweep rather than derived analytically, and it held at the realistic bucket-count scale beaconing's
own score-gate produces.

### STL seasonal residual on scenario 6 — the detector's own target, measured honestly

**STL does not cleanly detect the scenario it exists to catch.** Scored on the real
`seasonal_deviation` eval file: 0 of 36 malicious lines recovered when the victim
(`kgoldstein@corp.example`) is scored in isolation. The corpus-wide table above shows 43.3% mean
recall and "4/6 scenarios detected" for STL, but that number is misleading on its own: STL fires
broadly across the whole org (11.4% background false-positive rate, next section) and incidentally
sweeps up a fraction of *every* scenario's malicious lines by sheer coverage — it detects
`c2_beaconing` (92.5% recall), `data_exfiltration` (100%), `insider_mass_download` (65.7%), and
`prompt_injection_canary` (83.3%) at high recall for the same reason a coin that comes up heads 89%
of the time "detects" almost anything — but scores exactly **0%** on `seasonal_deviation` and
`low_and_slow_exfil`, the two scenarios where the campaign is specifically built to be subtle
rather than a volume spike. See [prediction 3](#pre-registered-predictions--measured-against-real-numbers)
above for the root-cause analysis (self-inclusive fit diluting a deliberately subtle, budget-capped
shift). `tests/test_signal_stl.py` independently confirms the mechanism is sound against a clean,
non-adversarial synthetic off-hours burst (100% recall, 4/4 injected hours) — the gap is specific
to scoring against an adversarially-subtle campaign built to defeat exactly this kind of check, not
a broken implementation.

Two real, measured implementation bugs were caught and fixed while building this detector against
real generated data (not hypothesized in the abstract):

1. **Floating-point noise on a near-degenerate residual population.** A highly regular entity's
   `MSTL` residual can be numerically zero (`~1e-15`) but not *exactly* `0.0`; `robust_z`'s
   documented MAD==0 policy only triggers on an exact zero, so a population of near-zero-but-
   distinct floats produced a tiny nonzero MAD and any hour "less perfectly zero" than its
   neighbours scored a spurious finite `|z| > 3.5`. Fixed by rounding residuals to 6 decimal places
   before scoring (`STL_RESIDUAL_ROUND_DECIMALS`, `constants.py`).
2. **Idle-hour population contamination.** The dense zero-filled grid `MSTL` needs for a correct
   seasonal fit was also being used as the `robust_z` *scoring* population — the exact MAD-
   degeneracy failure mode `burst.py`'s own docstring already names for a different detector,
   reproduced here one layer downstream: a mostly-idle entity's residual population is dominated by
   correctly-predicted-near-zero idle hours, so an entirely ordinary active hour reads as a huge
   outlier purely because idle time was allowed to define "normal." Fixed by restricting both the
   scoring population and the flagged-hour set to the entity's own *active* hours, matching
   `burst.py`'s established precedent exactly (module docstring, "Dense grid for decomposition,
   active-only population for scoring").

Both fixes reduced the *false-positive* rate substantially (an early, unfixed version flagged over
50% of all events org-wide) but did not close the recall gap on scenario 6 itself — the remaining
false-positive rate (below) and the miss on scenario 6 are reported as measured, not tuned further
after seeing these specific numbers, per this project's own stated discipline.

### URL path analysis — no scenario in this suite tests it, and that is stated plainly

**0/6 detected is expected, not a failure signal**, because none of the eight docs/11 scenarios
construct a C2/exfiltration campaign that encodes a beacon ID or data in the URL *path* specifically
(the closest, `c2_beaconing`, varies timing and domain, not path structure) — there is nothing in
this eval suite for this detector's specific technique to catch. Its own dedicated unit tests
(`tests/test_signal_url_path.py`) prove the mechanism works: a synthetic fixture with 25 ordinary
hyphenated-REST-path pairs plus one pair using random 32-character hex tokens
(`/api/v2/c7f3a9e1b2.../checkin`, docs/04's own worked example) is scored, and only the hex-token
pair is flagged, on both `mean_path_entropy` and `segment_random_ratio`. A real, measured false-
positive risk was caught and fixed while building the token-matching heuristic: a naive
"base64-ish charset" check alone flags ordinary hyphenated English phrases (`check-in-endpoint` is
entirely within `[A-Za-z0-9_-]`), and first-order character Shannon entropy does *not* discriminate
here either (a 17-25 character hyphenated phrase measures 3.3-3.8 bits/char, *higher* than a
same-length random hex string's 2.9-3.5 — natural language has low *conditional* entropy given
prior characters, not low marginal character-frequency entropy). Fixed with two structural checks
instead (`constants.py`'s `URL_PATH_TOKEN_MIN_DISTINCT_CHARS` docstring has the full reasoning):
minimum distinct-character count, and — for the base64-ish branch specifically — a mixed-case
requirement (genuine base64 tokens routinely mix case; REST slugs are conventionally all-lowercase).
All 12 realistic hyphenated-phrase examples tried during development are correctly rejected; the
hex worked example is correctly accepted.

implementation bug: a highly regular, low-natural-variance entity's post-decomposition residual

from 4 events/hour to 3) exceed `|z| > 3.5` routinely — the same class of instability a fixed
z-score threshold has on any near-deterministic low-count process. `robust=True` (LOESS's own
standard outlier-resistant fitting option) was tried directly and did not change this, ruling out
ordinary LOESS noise sensitivity as the cause. URL path analysis's 0.83% is comfortably in line with
every other detector's own load-bearing threshold choices in this module (`rarity`/`burst`'s own
documented thresholds) and was not adjusted after seeing this number.

## Known weaknesses

Stated honestly, per docs/12's own instruction.

1. **STL does not detect its own target scenario at adequate precision.** Reported at length above
   — a self-inclusive fit dilutes a deliberately subtle campaign, and the detector's baseline false
   positive rate (11.4%, concentrated on service accounts) is too high for production as shipped.
   The production fix implied by the root-cause analysis — score against a lagging, pre-period-only
   fitted profile rather than a self-inclusive one — requires persisted cross-analysis history this
   milestone's single-file batch harness does not have, the identical caveat `ml/features.py`'s
   `estimate_work_hours` already states for the same reason.
2. **Mahalanobis's false-positive rate roughly tripled** relative to M8's report (16.6% vs. M8's
   0.6%) on the wider, entity-relative-feature-inclusive vector — not investigated to a root cause
   this wave, flagged as a real regression worth a follow-up.
3. **Prediction 2's falsification suggests LOF's marginal value may be smaller than argued**, now
   that department-cohort features are explicit inputs every model can read — Mahalanobis
   out-detected LOF on its own target scenario (peer_group_deviation, 0.453 vs. 0.026 recall). LOF
   is still the only model whose entire premise is *local* relative comparison rather than a global
   one, and it remains cheap to fit and score, but this run does not support "LOF alone sees
   peer-group deviation" as stated.
4. **URL path analysis is untested by this eval suite specifically** — 0/6 "detected" reflects no
   scenario using this technique, not detector failure; its own unit tests are the only evidence of
   correctness on this technique until a future scenario exercises it end to end.
5. **Global models, not per-entity baselines**, restated from M8: all five L3 models fit one
   distribution across the whole org. The entity-relative *features* (6 of 53) partially address
   this without requiring a fully personalized model architecture, but a model like Mahalanobis
   still fits one global covariance over those features, which is part of why it both over-detects
   (6/6, via the now-explicit cohort dimensions) and over-flags benign traffic (16.6% FP).
6. **Interim, uncalibrated confidence**, restated from M8: `signals.confidence` is a percentile rank
   against a benign-training-corpus sample, not M10's isotonic calibration (not built yet).
7. **Synthetic-data circularity**, restated from M8 and docs/04's own caveat.
8. **No live pipeline wiring**, restated from M8 — `detect.py`/`run_signal_layer` produce signals
   from a features `DataFrame`/event rows; persisting into the live `signals` table is
   `app/pipeline`/`app/storage` integration work, out of this milestone's ownership.
9. **`make train`/`make eval` are still not wired to these scripts** (M16's job, docs/13). Run this
   milestone's benchmark directly — commands below.

## Reading the winner correctly

`ml.iforest`'s win is driven almost entirely by one scenario: it gets a **perfect 1.0/1.0/1.0** on
`data_exfiltration` and is **completely silent (0 recall) on the other seven** attack scenarios,
including `password_spray` and `insider_mass_download`, where `ml.autoencoder` gets useful partial
recall. Mean F1 rewards that one perfect hit over autoencoder's broader-but-noisier coverage
because seven zeros plus one 1.0, averaged, still edges out eight small-but-nonzero numbers
(`0.125` vs. `0.029`). `ml.autoencoder` has almost 5x `ml.iforest`'s AUC-PR (0.292 vs. 0.173) — the
threshold-free ranking metric — and detects six of eight scenarios instead of one, at the cost of
a much higher false-positive rate (below). This is exactly why docs/12 asks for F1, AUC-PR, and
per-scenario recall together instead of picking one: any single number here tells a different,
incomplete story.

**Per the pre-registered decision rule (stated in `evaluate.py` before this run, not chosen after
seeing the numbers), `ml.iforest` ships as primary.** Given the above, that is a legitimately
fragile win, not a strong one — docs/04's own instruction to "keep the others as ensemble members
with fusion weights" is doing real work here: `ml.autoencoder`'s broader, if noisier, recall is
exactly the kind of signal a fused, calibrated score (M10, not built yet) should combine with
`ml.iforest`'s high-precision hits rather than discard.

## Scenario 8 — low-and-slow exfil, the autoencoder's own test

docs/11: "Scenario 8 exists specifically to test whether the autoencoder earns its slot: low-and-
slow exfil is invisible to per-feature thresholds and only detectable through the joint
distribution." **None of the three models detect it in this run** — recall is 0.0 across the
board, and AUC-PR is at (`ml.iforest` 0.0016, `ml.mahalanobis` 0.0016) or barely above
(`ml.autoencoder` 0.0081, ~4.6x) the 0.0018 random baseline implied by 42 positive rows out of
23,128. This is the honest result, reported as such rather than reframed.

**This does not contradict the scenario's own acceptance gate**, which independently proved (at
generation time, `s08_low_and_slow_exfil.py`'s `_check_acceptance`) that a Mahalanobis distance
computed **per victim**, on that victim's own seven core features and own benign history, separates
≥70% of attack hours above that victim's own p95. The model in this report is a different, harder
problem: **one global covariance/manifold fit across the entire org's population** (all ~262
principals, all their windows, pooled) rather than a personalized per-entity baseline. Precisely:
of the 50 features, only `n_events_z_vs_own_history`, `bytes_out_z_vs_own` (per-entity, own-history
relative) and `n_events_z_vs_cohort` (peer-relative) are anything other than an absolute,
population-level measure — **47 of 50 are absolute**. A population-wide covariance or a manifold
trained to reconstruct every principal's typical behavior has far more freedom to absorb one
victim's subtly-shifted joint pattern across those 47 absolute dimensions than a model that only
ever sees that one victim's own history the way the acceptance gate's own check does.
**This is a genuine, useful finding, not an excuse**: it suggests the eventual production answer
for this class of attack is closer to `ml.peer_group` (docs/04's peer-group-relative model,
scenario 7's own detector, not built in this milestone) or a per-entity/per-cohort baseline than
to a single org-wide model — exactly the kind of result a benchmark is supposed to surface. This is
now recorded in `docs/04-DETECTION.md`'s L3 feature-vector section as a measured defect in the
feature list itself, not just a modeling footnote. **This is exactly the defect the entity-relative
feature work at the top of this file addresses — 6 of 53 features are now entity-relative, up from
3 of 50 — see the current report above for the measured effect (prediction 1: confirmed).**

## Known weaknesses

Stated honestly, per docs/12's own instruction that naming your own weaknesses is what a senior
engineer does.

1. **Global models, not per-entity baselines.** All three models fit one distribution across the
   whole org. Scenario 8's null result (above) is the clearest evidence this matters; it likely
   also explains part of the weak showing on `impossible_travel` and `account_takeover_chain`
   (both very low-volume injections — 4-5 events each — that a personalized baseline would have
   an easier time flagging as "unlike this specific principal" than a pooled model does).
2. **Interim, uncalibrated confidence.** `signals.confidence` here is a percentile rank against a
   held-out *benign-training-corpus* sample, not the isotonic-regression calibration docs/04's
   "Fusion & calibration" section specifies (M10, not built yet). The false-positive-rate section
   above shows this concretely: the same nominal "99.5th percentile" threshold produces a 0.0%,
   0.6%, and 3.4% actual flag rate for the three models respectively on a *different* org's
   traffic than it was calibrated on.
3. **Synthetic-data circularity**, restated from docs/04's own caveat: every model here is trained
   on `datagen`'s benign corpus and partly learns that generator's own distribution, not
   necessarily a real enterprise's. Mitigated, not eliminated, by `datagen`'s real-world-grounded
   distributions (domain popularity, UA mix, diurnal curves) per docs/11.
4. **Estimated work hours, not real ones.** `estimate_work_hours` (`features.py`) infers each
   entity's "business hours" from its own event timestamps rather than from an HR feed, because a
   real deployment has no such feed. It is self-inclusive of the window being scored — see that
   function's own docstring for the stated (and here, not triggering) failure mode on a very long
   low-and-slow campaign.
5. **Very low positive counts on several scenarios** (`impossible_travel` n=4,

## Reading the L3 table: the F1 winner is not the better model

Isolation Forest wins the pre-registered metric (mean F1 at a fixed threshold, 0.125 vs 0.029) and
that win is hollow. Its entire score comes from one perfect hit on `data_exfiltration`; it is
silent on the other seven scenarios — **1 of 8 detected**. The autoencoder detects **6 of 8**, with
5x the AUC-PR (0.292 vs 0.173) and 5x the recall.

AUC-PR is threshold-free and F1 is not, so the two metrics are measuring different things here:
the autoencoder *ranks* anomalies far better and *places its threshold* far worse. Precision 0.016
means it flags broadly at the shipped cut point.

The honest conclusion is therefore not "ship Isolation Forest". It is that neither model is
shippable as-is, and the autoencoder's deficit is calibration — precisely what M10's per-detector
isotonic regression exists to correct. **This benchmark must be re-run after calibration before
either model is declared primary.** Reporting the F1 winner without this paragraph would be
technically true and materially misleading.
