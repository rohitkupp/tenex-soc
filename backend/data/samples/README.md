# Sample logs

ZScaler NSS web-proxy logs in the real tab-separated format, header row included — the same
shape `app/parsers/zscaler.py` sniffs and parses in production. Generated by `datagen` with fixed
seeds, so regenerating them produces byte-identical files.

**Full width, not a demo-only trimmed shape.** Each row carries all 181 documented NSS fields
(`docs/v1/zscaler-nss-web-fields.md`) — the same 25 docs/03 originally mapped, the 27 promoted
since, and ~129 more the field-reference catalogue documents but `app/parsers/zscaler.py`
deliberately does not extract (device/asset detail, DLP dictionary hit-counts, TLS cipher/cert
detail, cloud-app instance identifiers, ...). A real customer's NSS feed is configured with
however many fields their admin turned on — these samples are what "every field" looks like, so
uploading one exercises the same 181-vs-52 extraction the app runs against in production, not a
narrower shape a reviewer would never actually see. `docs/v1/11-SYNTHETIC-DATA.md` "Extraction
contract" has the full generator/parser split.

All three parse at **100%** (`ZScalerParser`, 0 failures across 17,319 lines / 181 columns each).

| File | Lines | Size | What's in it |
|---|--:|--:|---|
| `01-mixed-week.log` | 8,749 | 12.6 MB | **Start here.** One week of a simulated 250-person org, with three attack campaigns (C2 beaconing, data exfiltration, low-and-slow exfil — the last needs a large background window to clear its own statistical acceptance check, which is why this file can't shrink much below ~8k events) and one benign-but-weird decoy hidden in ordinary traffic |
| `02-c2-beaconing.log` | 4,360 | 6.3 MB | Single campaign: C2 beaconing (T1071.001) — regular-interval callbacks with jitter |
| `03-data-exfiltration.log` | 4,208 | 6.1 MB | Single campaign: exfiltration to cloud storage (T1567.002) — large POSTs to a new domain |

Bigger than the pre-full-width versions of these files: at 181 columns a row is ~4.8x the bytes it
was at 52, and event counts here are unchanged from before (`01`: 10k background events target,
`02`/`03`: 4k each — see "Regenerating"). See "Uploading" for why that is not a problem for any of
the three upload paths this product actually has.

Each `.log` ships with a `.labels.json` holding **ground truth**: the exact line numbers that are
malicious, the campaign's ATT&CK technique, and the victim principal. That is what makes these
useful beyond a smoke test — you can check what the system found against what was actually there,
which is the same comparison `evals/` runs.

```jsonc
{
  "log_file": "...", "seed": 99, "org_fingerprint": "...",
  "total_lines": 8749, "window_start": "...", "window_end": "...",
  "scenarios": [ { "technique": "T1071.001", "malicious_line_numbers": [ ... ] }, ... ]
}
```

## What to expect

`01-mixed-week.log` contains **592 malicious lines out of 8,749 — 6.8%**. That ratio is
deliberately generous for a demo. Real proxy traffic is far quieter, and the eval corpus in
`evals/results.md` is scored at realistic ratios where per-scenario recall drops sharply; do not
read demo behaviour as benchmark performance. The benchmark numbers are the honest ones.

The fourth injected campaign in `01-mixed-week.log` is `benign_but_weird` — unusual activity that
is **not** an attack. It is there so you can see what the system does with a false-positive
candidate, not only with true positives.

## Uploading

One file per analysis. Incidents are formed by correlating entities *across* the whole file, so
a bigger window generally yields richer incidents than several small ones.

**No practical size limit on any of the three files, on any upload path this product has.**
`app/api` caps a single upload at 200 MB regardless of environment — all three files here are
under 13 MB, nowhere close.

An earlier version of this note warned that "the deployed demo" proxies uploads through Vercel and
caps them near ~4 MB — that was never true of the upload path specifically, and is worth stating
plainly since it shaped this directory's file sizes for a while. `frontend/lib/api/upload.ts` (the
browser's only upload code path) sends the file with `XMLHttpRequest` straight to the API's own
origin (`API_URL`, not the same-origin Next.js rewrite `next.config.ts` uses for authenticated
JSON calls) specifically to avoid Vercel's serverless body-size ceiling — its own module docstring
states this is deliberate, and `deploy/README.md` documents the same decision from the deployment
side ("uploads go browser → API directly, never through Vercel"). The Vercel proxy `next.config.ts`
sets up is real and does cap *other* API calls' bodies, but the upload endpoint was specifically
engineered around it, not shaped by it. Running locally with `make up` also has no upload size
limit — the browser reaches the API directly there too, by construction rather than by design
decision.

## Regenerating

```bash
cd backend
python -m datagen demo     --events 8000 --window-days 7 --seed 99 --out data/samples
python -m datagen scenario --name c2_beaconing      --events 4000 --seed 21 --out data/samples
python -m datagen scenario --name data_exfiltration --events 4000 --seed 22 --out data/samples

# The CLI names files after the command, not this directory's numbering — rename to match:
cd data/samples
mv demo_mixed.log 01-mixed-week.log && mv demo_mixed.labels.json 01-mixed-week.labels.json
mv scenario_c2_beaconing.log 02-c2-beaconing.log
mv scenario_c2_beaconing.labels.json 02-c2-beaconing.labels.json
mv scenario_data_exfiltration.log 03-data-exfiltration.log
mv scenario_data_exfiltration.labels.json 03-data-exfiltration.labels.json
```

`01-mixed-week.log` uses `--events 8000`, not the round `10000` the pre-full-width version of this
file used: `low_and_slow_exfil`, one of its three injected campaigns, needs enough background
volume to clear its own statistical acceptance check (docs/11), and 8000 is the smallest value
that reliably does so. `02`/`03` are unchanged from before at `4000` each.

`python -m datagen all` regenerates the full corpus and every eval scenario instead — that is what
`make gen-data` runs, and it writes to the gitignored `data/corpus` and `data/eval` directories
rather than here.
