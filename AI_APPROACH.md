# Anomaly Detection Approach

The anomaly-detection pipeline is organized into three layers. Each layer looks at the proxy logs from a different perspective: **L1 catches known suspicious conditions, L2 detects specific mathematical/security patterns, and L3 uses unsupervised ML to identify broader deviations from normal behavior.** All three produce a common `Signal` containing the affected entity, time window, score, explanation, and supporting event IDs.

## L1 — Deterministic Security Rules

L1 is the fastest and most deterministic layer. Eleven Sigma-style YAML rules are compiled into SQL and run directly against the normalized events in PostgreSQL, so the database performs the filtering and time-window calculations rather than Python iterating over every event.

The rules check for:

- **Known Zscaler threat name** in an event.
- **Malware, phishing, or C2 URL category.**
- **Blocked → allowed to the same host within five minutes**, which can indicate a successful retry after a security control blocked the original request.
- **DLP trigger on outbound traffic.**
- **Executable/archive download from a new or uncategorized domain.**
- **Large POST (>10 MB) to a new or uncategorized domain**, which may indicate unusual outbound data transfer.
- **Anonymizer/VPN/proxy-avoidance traffic.**
- **Zscaler risk score ≥80** on an otherwise allowed request.
- **Credentials contained in a URL query string.**
- **Direct-to-IP HTTP traffic** instead of normal domain-based access.
- **Non-browser clients** such as `curl`, `wget`, PowerShell, or `python-requests`.

Because these are deterministic rules rather than ML models, their initial scores are based on fixed severity levels: informational `0.20`, low `0.35`, medium `0.55`, high `0.75`, and critical `0.90`, with small adjustments when a threshold is exceeded by a large amount. These are treated as **raw evidence scores**, not literal probabilities of an attack.

## L2 — Mathematical and Specialized Detectors

L2 looks for behaviors that are harder to express as simple SQL conditions. Six detectors currently run.

**Beaconing** looks for repeated communication between a source IP and domain at highly regular time intervals. It measures variation in the time between requests and also uses FFT analysis to identify strong repeating periods. More regular, longer-lasting communication with more observations produces a higher score.

**Burst detection** identifies sudden spikes in traffic. User and source-IP activity is grouped into five-minute windows and compared with that entity's own normal active periods using a robust median/MAD z-score. Activity beyond roughly `|z| > 3.5` is treated as anomalous, with larger deviations producing stronger evidence.

**DGA detection** identifies domains that resemble names automatically generated by malware. It uses a trained logistic-regression classifier over five characteristics: Shannon entropy, character-bigram likelihood, digit ratio, longest consonant run, and domain length. The classifier produces a probability-like score through logistic regression, with `0.5` as its initial decision threshold.

**Domain rarity** measures how infrequently a destination appears in the organization's traffic. Its basic score is:

`1 / (1 + domain event count)`

so rarely observed domains receive higher scores.

**STL residual detection** models normal daily and weekly request-volume patterns and removes the expected trend and seasonality. It then examines the unexplained residual activity; unusually large residual z-scores indicate behavior that remains abnormal even after accounting for normal time-of-day and day-of-week patterns.

**URL-path entropy** looks for unusually random-looking or machine-generated URL paths. It combines Shannon entropy with structural checks and compares activity with other requests to the same domain. Extremely unusual values—currently around the 99.5th percentile—are flagged.

Each L2 detector therefore produces a score in the units that make sense for that detector—regularity, z-score, rarity, classifier output, residual, or percentile. Those values are normalized later through the common calibration step rather than treating the raw mathematical value as directly comparable across detectors.

## L3 — Unsupervised Behavioral Anomaly Detection

L3 is intended to identify unusual behavior that was **not explicitly anticipated by an L1 rule or L2 detector**.

Rather than sending individual log entries into the models, traffic is aggregated into **one-hour windows for each user and source IP**. Each window becomes a 58-feature behavioral profile covering request volume, timing, domain activity, upload/download behavior, HTTP characteristics, infrastructure/device information, identity activity, and navigation. The features also include deviations from the entity's own history and, for users, from their department cohort.

Three complementary unsupervised models currently score these windows.

**Extended Isolation Forest (EIF)** asks how easily a behavior can be separated from normal traffic. It repeatedly partitions the feature space with random hyperplanes; unusual observations tend to become isolated after fewer splits.

**k-th Nearest Neighbor** asks how far the current behavior is from its closest historical examples. If even its 20th-nearest neighbor is far away, the activity is considered unusual.

**Local Outlier Factor (LOF)** compares the density around an observation with the density around its neighbors. This helps distinguish a genuine local outlier from a point that simply belongs to a naturally sparse behavioral population.

In short:

- **EIF:** How easy is this activity to isolate from the overall population?
- **k-thNN:** How far is it from similar historical activity?
- **LOF:** Is it unusually isolated relative to its local neighborhood?

In a production environment with representative historical data and confirmed incidents, I would benchmark these models on precision, recall, false-positive rate, and incident coverage and either select the best-performing model or retain multiple models only if the combination provides measurable additional value. The current prototype runs all three because the available evaluation data is synthetic and the models capture different definitions of "unusual."

## Confidence Calibration

The raw outputs from these layers are not naturally comparable. A `3.8` LOF score, a `0.82` beaconing score, and a `0.75` Sigma-rule score all mean different things.

For the L3 models, the first normalization step compares a new anomaly score with the model's score distribution on held-out benign traffic. For example, a score at the `99.7th percentile` means:

> This behavior was more anomalous than approximately 99.7% of the benign reference traffic.

It does **not** mean there is a 99.7% chance that the behavior is malicious. L3 currently emits a signal when the score exceeds the **99.5th percentile** of its benign reference distribution.

After L1, L2, and L3 run, the system applies a second common calibration step using a **per-detector isotonic regression model** trained on held-out evaluation data. This maps each detector's raw evidence into a more comparable confidence score. If a detector does not yet have a fitted calibrator, the system explicitly marks it as uncalibrated and falls back to its normalized raw score instead of representing it as a calibrated probability.

This gives the downstream system a consistent way to combine evidence from very different detectors.

## Correlation — Signals into Incidents

The correlation service does **not detect new anomalies**. Its job is to determine which L1/L2/L3 signals are likely describing the **same underlying security incident**.

It builds a graph where nodes represent entities such as users, source IPs, destination IPs, domains, ASNs, and countries. Relationships observed in the proxy traffic become edges between those nodes.

Any entity carrying a detection signal becomes a **seed**. The system expands each seed to its immediate graph neighbors so that non-flagged entities can provide connective context—for example:

`User → suspicious domain → destination IP`

The resulting subgraph is clustered using the **Louvain community-detection algorithm**, which finds groups of entities that are more densely connected to one another than to the rest of the graph. Each community containing suspicious seed entities becomes a candidate incident, and heavily overlapping communities are merged.

This is how the system can turn many individual detections such as:

`rare-domain signal + EIF anomaly + beaconing signal + large POST rule`

into a single incident describing one connected security story rather than presenting four unrelated alerts.

Finally, the calibrated detector confidences within each incident are combined using a weighted **noisy-OR fusion**. Only the strongest signal from each detector is used, and detector weights account for measured reliability. A small graph bonus rewards corroboration across multiple detector layers and communities with a higher concentration of suspicious entities. The resulting fused score determines the incident's anomaly confidence, severity, and queue priority.

The LLM operates **after this entire process**. It does not detect anomalies or change these scores; it uses the already-generated events, signals, incident score, and supporting evidence to explain what happened and why it may matter to a SOC analyst.

## Triage — LLM-Based Incident Analysis

After correlation groups related signals into incidents, the **Triage stage** uses an LLM to interpret the evidence and turn the machine-generated findings into something a SOC analyst can quickly understand.

The important distinction is that the LLM does **not** perform anomaly detection and does **not** change the incident's anomaly score, severity, or queue priority. Those values have already been calculated deterministically by the detection, calibration, and correlation stages. The LLM receives the incident along with its supporting events, signals, confidence scores, and relevant threat-intelligence context.

For each incident, the triage flow includes several steps:

- **Analyst:** Reviews the incident, its underlying events and signals, and relevant threat knowledge to form a security hypothesis and explain what behavior was observed.
- **RAG / Threat Knowledge:** Retrieves relevant cybersecurity context, primarily from the MITRE ATT&CK knowledge base, so that technique mappings and security explanations are grounded in known detection guidance rather than generated from memory alone.
- **Verifier:** Programmatically checks that the LLM's claims are supported by the actual evidence, that cited event IDs exist, and that numerical values and citations match the underlying data.
- **Judge:** Reviews the proposed explanation against a structured rubric, including whether claims are supported, whether observations are clearly separated from conclusions, whether benign alternatives were considered, and whether the stated confidence is appropriate.
- **Presenter / Summarizer:** Produces the final SOC-facing explanation, including the incident summary, supporting evidence, possible ATT&CK techniques, and a chronological timeline of relevant activity.

The system also keeps **anomaly confidence** separate from **threat confidence**. Anomaly confidence comes from the mathematical detection and fusion pipeline and represents how unusual the behavior is. Threat confidence is the LLM's assessment of how strongly the available evidence supports a malicious security hypothesis. Something can therefore be highly anomalous without the system claiming that it is definitely malicious.

This separation is intentional: the deterministic pipeline answers **"How unusual is this activity?"**, while the Triage stage answers **"What might this activity mean, what evidence supports that interpretation, and what should the analyst look at next?"**
